# CEO Plan: bm25 hot-path hardening

Generated by /plan-ceo-review on 2026-07-25
Branch: main | Mode: SELECTIVE EXPANSION
Repo: sliday/tamp

## Context

A prior session fixed retrieval quality in the `bm25-trim` stage (identifier subtoken
expansion, block-aware dropping, rerank signals, offline eval harness). That work is
written, tested (656/656), and uncommitted on `main`.

This review audited that work, found two defects in it and one in its own benchmark, then
survived an adversarial re-review that found six more. All measurements below were
re-verified after that re-review; two of the original numbers were wrong and are corrected.

## Findings

**1. HIGH — quadratic regex introduced on the `bm25-trim` path.**
`STRINGS_RE` in the new `lib/code-chunks.js` backtracks quadratically. The cost is the
`g`-flag restart after a failed match — the engine scans O(n), fails to find a closing
quote, advances the start position by one, and scans again.

Generator: `'"' + 'a\\"'.repeat(n)` (an escaped-quote run with no clean terminator).

| input | time |
|---|---|
| 6,001 chars | 8 ms |
| 24,001 chars | 99 ms |
| 96,001 chars | 1,754 ms |
| 192,001 chars | 6,838 ms |

4x input, 12-18x time. Triggers on minified bundle lines, JSON-in-JS blobs, regex-heavy
lines — all plausible inside a >64 KB `tool_result`.

The three other regexes added in the same change (`DEF_RE`, `PY_BLOCK_RE`, brace sniff)
probe clean at 64 K: all sub-millisecond.

*Severity is HIGH, not CRITICAL.* `lib/code-chunks.js` has exactly one importer
(`lib/bm25.js:14`), which runs only under `stages.includes('bm25-trim')` — L8, while
`DEFAULT_LEVEL = 5`. A user must opt in before this can fire.

**2. HIGH — the `countTokens` tax is codebase-wide; the prior fix was scoped to one stage.**
`countTokens` has a fixed floor of roughly 22 ms per call *plus* a proportional term
(~22 ms at 100 B-10 KB, ~33 ms at 100 KB, ~134 ms at 1 MB; pathological single-token-run
input is far worse). The floor dominates on small inputs, which is what made per-line
calling catastrophic; the proportional term bites on exactly the >64 KB targets this work
concerns.

Call sites paying it per target:
- `compress.js:708-740` — two calls per target in the stats early-return branches
  (dedup, diff, read-diff, graph, disclosure, bm25-trim, redact).
- `compress.js:410`, `:464`, `:492`, `:584-585`, `:601` — two calls per target inside
  `compressBlock`, which is where a *first-seen* `tool_result` goes (`:732`). The
  early-return branches only fire on repeat content, so `compressBlock` carries the
  majority of the tax on a typical request.

At `DEFAULT_LEVEL = 5` the active stage set is `L5_STAGES` (base + `llmlingua`,
`read-diff`, `prune`), plus always-on `redact`. `disclosure` is L8 and `graph` is L9 —
neither is default. `bm25-trim` is L8. The `compressBlock` sites are on the default path
regardless.

**3. MEDIUM — the benchmark's before/after comparison is confounded, and its NDCG gate is weak.**
`bench/retrieval-eval.js:302-303` runs `evaluate(legacyTokenize, false)` against
`evaluate(tokenize, true)` — the two arms differ in *two* variables (tokenizer and rerank),
so the headline "NDCG 0.348 → 0.931" cannot attribute the gain to either. Measured across
all four arms:

| tokenizer / rerank | mean NDCG | mean recall | defRecall |
|---|---|---|---|
| legacy / off | 0.348 | 0.400 | 0.533 |
| legacy / on | 0.441 | 0.467 | 0.533 |
| new / off | 0.770 | 0.733 | 1.000 |
| new / on | 0.931 | 1.000 | 1.000 |

So the tokenizer carries most of the gain (0.348 → 0.770) and rerank adds the rest. The
reported figure was not wrong, but it was not attributable.

The *definition-survival* gate at `:327-331` is already absolute (`defRecall < 1` fails).
Only the NDCG and recall checks are purely relative, so with means of 0.348 and 0.931 the
current NDCG could collapse to 0.36 and those two checks would still pass forever.

**4. MEDIUM — `rerankScores` ignores the injectable `tokenizer`.** It uses module-level
`tokenize` at `lib/bm25.js:174` for the definition-name lookup while `bm25Scores` and
`trimLinesByRelevance` both honour the parameter. Harmless today only because the bench
runs the legacy arm with rerank disabled.

**5. PROCESS — AGENTS.md violation.** "Never push to main — create `feat/` or `fix/`
branches and open a PR." All work sits uncommitted on `main`, alongside ~12 unrelated
untracked paths (`site/`, `video/`, `presentation.html`, `PRD.md`, `codedb.snapshot`,
`.DS_Store`).

**6. RETROSPECTIVE — recurring defect site.** `v0.8.11` killed three quadratic ReDoS
regexes on this path. `v0.8.14` fixed a bm25 anchor bug. This review found a fourth
quadratic regex and a missed tokenizer tax on the same path. Four data points, one pattern:
the compression hot path has no automated defence against the two defect classes it keeps
producing. That observation is what the accepted expansions attack.

## Vision

### 10x check

Today every lossy or hot-path stage in Tamp is defended by code review and by whoever
happens to profile it. Review demonstrably missed all four defects above — the same person
who wrote the code found them only by deliberately probing, and an adversarial second pass
found six more issues in the write-up of those findings.

The 10x version: the hot path defends itself. Adversarial input timing and tokenizer-call
counts are build-failing assertions, and lossy stages carry retrieval-quality numbers that
regress loudly. A contributor — human or agent — cannot land defect number five without
the suite saying so.

*Honest bound on this plan:* the accepted scope delivers that for `bm25-trim` only. The
other four lossy stages (`llmlingua`, `textpress`, `disclosure`, `prune`) remain unmeasured
— see E5, deferred.

## Implementation approach

> **REVISED after the outside voice (Codex).** Two approved decisions changed. The scanner
> rewrite is **out** — replaced by a per-line length cap (T1-A). The global estimator
> contract is **out** — replaced by estimate-subsets / count-replacements (T2-A). Sections
> below marked SUPERSEDED are kept for the record of why. Sequencing changed too (T4-A).

### Superseded: the scanner rewrite

Approach C originally specified a 60-90 line character scanner. Codex countered that
`detectBlocks` already treats `null` as a valid fallback, so a **per-line length cap before
`stripNoise`** bounds the work at a fraction of the cost. Measured:

| line length | uncapped | capped at 2,000 |
|---|---|---|
| 24,001 chars | 105 ms | 0 ms |
| 96,001 chars | 1,712 ms | 0 ms |
| 192,001 chars | 6,592 ms | 0 ms |

The cap fully bounds the defect in roughly one line. It sacrifices block detection only on
lines over the cap, where block-aware trimming was near-worthless anyway.

Codex also observed that `BRACE_EXT` claims JavaScript, Rust, C++, C#, Swift and PHP, and
that one scanner cannot correctly handle JS templates, Rust raw strings, C# verbatim
strings and C++ raw strings under the stated rules. That kills the scanner's main
justification: it buys correctness it cannot actually deliver, at 60x the size.

**The earlier elimination of "Approach A" was narrower than it read.** What was measured
and eliminated was one specific minimal variant — a Friedl-unrolled regex, which is also
quadratic and ~2x slower. A length cap was never evaluated. That was a real gap in this
review, found by the outside voice.

*Consequence:* the `"/*"`-inside-a-string mis-parse stays unfixed, and the rescan-raw rule
(T3-A) is moot — there is no scanner to put it in. Both are recorded in TODOS as the
follow-on if block detection is ever revisited.

### Adopted work

The obvious minimal patch — rewriting `STRINGS_RE` with Friedl unrolling
(`"[^"\\\n]*(?:\\.[^"\\\n]*)*"`) — was proposed during adversarial review and **tested. It
is also quadratic, and about 2x slower than the original** (14 ms / 236 ms / 3,720 ms /
14,634 ms across the table above). Unrolling removes inner-alternation backtracking, which
is not where the cost is. The cost is the `g`-flag restart. Only a single-pass scanner
removes it. Approach A is therefore eliminated on measurement, not on taste.

1. **Character scanner replaces `stripNoise` in `lib/code-chunks.js`.** Deletes
   `STRINGS_RE` and `LINE_COMMENT_RE`, folding string/comment/brace state into the
   per-character loop that already exists in `detectBraceBlocks:102-116`.

   *Language contract to be written into the code:* models single-quote, double-quote and
   backtick state; backslash escapes; `${...}` nesting depth inside template literals (a
   `}` closing an interpolation must not pop a block — something `STRINGS_RE` never
   attempted, since it swallowed the whole backtick span); `//` and `#` line comments;
   `/* */` across lines. Does **not** lex regex literals — an unbalanced result there
   returns `null` and falls back to line trimming, as today.

   *Cross-line string rule:* reset `'` and `"` state at newline; carry backtick state
   across lines. Without this an unterminated quote swallows the rest of the body and
   produces a false imbalance.

   *Regex-literal guard — a real regression the naive scanner would introduce.* Verified:
   `if (/['"]/.test(x)) {` today yields **2 blocks**, because `STRINGS_RE` needs a matching
   pair, finds none, and leaves the line intact so the `{` is counted. A quote-state scanner
   enters string state at the `'`, swallows the `{`, and the file goes unbalanced → `null`
   → block-aware trimming lost. `/['"]/` is a common JS idiom. **Rule:** if the scanner
   reaches end-of-line still inside `'` or `"` state, discard that line's quote handling
   and re-scan it raw before applying brace deltas. Preserves today's behaviour exactly,
   costs one branch. Add `if (/['"]/.test(x)) {` as a named test fixture.

   *Acknowledged behaviour change:* current code runs `/* */` detection before string
   stripping, so `"/*"` inside a string falsely opens a block comment. The scanner fixes
   that. Balance decides `null` vs block-aware trimming, so real outputs move.

   *Acceptance criterion:* `detectBlocks` returns non-null on the same fixtures it does
   today, and `test/code-chunks.test.js` is migrated rather than deleted.

   *Realistic size:* 60-90 lines of stateful code plus a test matrix, replacing 6 lines of
   regex. This is not a smaller diff. It is the only one that is linear.

2. **`rerankScores` accepts `tokenizer`,** matching its siblings.

3. **Tokenizer-call reduction — halve exactly, do not estimate globally.**

   *A global per-request ratio was designed, then measured, then abandoned.* Chars-per-token
   is not stable across content types. Measured on a mixed body (global ratio 2.53):

   | content | chars/token | error if estimated from the global ratio |
   |---|---|---|
   | prose | 4.64 | **+83.2%** |
   | json | 2.29 | -9.4% |
   | base64 | 1.71 | -32.3% |
   | code | 3.23 | +27.5% |

   Minified bundles and JSON-in-JS blobs are exactly the >64 KB payloads finding 1 cites.
   A ±10% accuracy bound is unachievable by that design, and the aggregate rewiring it
   forced was a consequence of a broken premise. Dropped.

   **Adopted design — one exact call per target instead of two:**
   - Count `originalTokens` exactly, once per target. Derive *that target's own*
     chars-per-token ratio from it and estimate `compressedTokens` from that ratio.
     Original and compressed share content, so the ratio is near-identical — unlike the
     cross-content-type spread above. This is the same self-calibration
     `lib/bm25.js:225` already uses, which is why it works there.
   - **bm25-trim targets cost zero extra calls.** `compress.js:190-191` already holds
     exact `target.bm25OriginalTokens` / `bm25TrimmedTokens` from `lib/bm25.js:211` and
     `:352`; `compress.js:728` currently recomputes both. Reuse instead of recount —
     exact *and* free.
   - Applies to `compress.js:708-740` **and** the `compressBlock` sites (`:410`, `:464`,
     `:492`, `:584-585`, `:601`). The early-return branches only fire on repeat content;
     a first-seen `tool_result` goes to `compressBlock` at `:732`, so that is where most
     of the tax lives.
   - **Aggregates need no rewiring.** `stats.js:57-58`, `stats.js:119`, `index.js:218`,
     `bin/ui/Dashboard.js:34` and `createSession` all sum per-target values. Originals
     stay exact, so the original-side totals stay exact. Only the compressed side is
     estimated.
   - **Honesty flag:** per-target stats carry `tokensEstimated: true` for the compressed
     value. `stats.js:69` renders the most user-visible number
     (`` `${s.originalTokens}→${s.compressedTokens} tok` ``) and should mark it, e.g.
     `→~N tok`. `bench/render.js:126,130,131,238` reads the same fields and mixes them
     with exact figures from `bench/runner.js:235,245` — either rewire it to exact counts
     or label the columns.
   - **Accuracy bound:** ±10% per target, now achievable because the ratio comes from the
     target's own text. Assert in `test/` (Stop-hook path) over the
     `bench/retrieval-eval.js` fixture corpus plus one minified and one base64 fixture.

   *Honest ceiling:* this halves the tax rather than eliminating it. Elimination required
   the global ratio, which the table above disproves.

4. **Ship hygiene.** Move to a `fix/` branch, **stage selectively** (`git add` named
   paths — `git add -A` would sweep the ~12 unrelated untracked paths into the PR), bump
   `package.json` version and add a CHANGELOG entry per the repo's release convention,
   open a PR.

### E1 — bounded scope and flake-proof design

*Guarded set (named, not "every regex on the hot path" — `lib/rewriters/` alone holds ~80
regex literals):* `lib/code-chunks.js` string/comment handling (or its scanner
replacement), `PY_BLOCK_RE`, the brace sniff, and `lib/bm25.js` `DEF_RE`, `COMMENT_RE`,
`INTRA_WORD_RE`, `CAMEL_ACRONYM`, `CAMEL_LOWER_UPPER`.

*Assertion shape: absolute wall-clock ceiling, not a growth ratio.* The clean regexes
measure ~0.35 ms at 64 K, so a ratio test compares noise to noise and one GC pause yields a
10x reading. `STRINGS_RE` measures **710 ms at 64 K** (the 1,754 ms figure is the 96 K row).
Assert **< 25 ms at 64 K input** — ~70x headroom above clean, and tight enough to catch a
regression 4x milder than `STRINGS_RE`. Include warm-up iterations and best-of-N.

*Adversarial input contract — the part that makes or breaks this guard.* The one recorded
generator is adversarial for `STRINGS_RE`, which item 1 **deletes**. Fed benign 64 K input
the other seven entries all measure <1 ms and the guard asserts nothing; it would not have
caught the original bug. Each guarded entry needs a recorded pathological generator, or a
shared pathological corpus: escaped-quote runs, unterminated delimiters, long single-token
runs, deep indentation, no-newline blobs. Without that E1 is a green-light generator.

*Why flakiness matters more than usual here:* `AGENTS.md:22` runs `npm test` in a Stop hook
on every completion, so a flaky timing test blocks the agent loop, not just a build.

### E2 — build path (the reason the estimate moved)

`countTokens` is a static ESM named import at `compress.js:4` and `lib/bm25.js:13`.
Counting calls requires one of:
- `node:test` `mock.module` — **unavailable on this repo's Node v22.22.3 without
  `--experimental-test-module-mocks`**, and the module under test would need dynamic import
  after mock installation. No test in this repo mocks a module today.
- **A `lib/tokens.js` wrapper** that re-exports a counting-instrumented `countTokens`, plus
  rewriting both import sites.

**Chosen: the wrapper.** No experimental flags, no dynamic-import dance, and it gives every
future caller one obvious place to look. The wrapper refactor is in scope; that is what
moved the estimate from ~3h to ~6h.

*Budget shape — it cannot be a constant.* `lib/bm25.js` legitimately spends calls per
trimmed target. Express it as a formula and assert against a fixed fixture request:
`calls ≤ 1 × (compressed targets) + 2 × (bm25-trimmed targets)`. After item 3 the bm25
term should fall to 0 via the reuse of `bm25OriginalTokens` / `bm25TrimmedTokens`, so the
budget doubles as the regression test for that reuse.
